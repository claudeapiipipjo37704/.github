<p>关于机房出口和住宅出口的差别，争论往往停在体感上。与其听结论，不如自己跑一遍。这篇记录的是一次两周对照：同一套脚本、同一批请求体、两条链路各跑七天，把失败类型、延迟分布、成本逐项记下来，最后说明这个结果能推广到哪、不能推广到哪。</p>

<h2>一、实验设计：两条链路、同一套脚本、各七天</h2>
<p>先把变量控制住。两条链路除了出口不同，其余全部一致：同一台机器、同一个 SDK 版本、同一批请求体、同样的并发曲线、同样的重试参数。任何一项不同，结论都不成立，做出来的数据只能算轶事。</p>
<h3>链路 A：机房出口</h3>
<p>云主机直连，出口地址的 ASN 属于云厂商。这是最常见的默认配置，也是被讨论最多的一种。为了让对照更干净，云主机的区域选在离目标接入点较近的机房，避免把地理距离的影响算进结论。</p>
<h3>链路 B：住宅出口</h3>
<p>同一台机器通过住宅代理出网，出口 ASN 属于当地宽带运营商，地址在一周内固定不变。代理协议、鉴权方式、超时参数与链路 A 保持一致，唯一的差异就是出口这一段。</p>
<h3>观测项与记录方式</h3>
<p>每次请求记录：时间戳、状态码、首字节耗时、总耗时、是否重试、重试次数。按小时聚合，保留原始日志。样本量控制在每天两千次左右，既能看出趋势，也不至于给服务端造成额外压力。</p>

<h2>二、第一周记录：机房出口的失败集中在哪</h2>
<p>第一周跑机房出口。整体成功率不算难看，但失败在时间上高度集中，这个分布本身就是信息，比一个笼统的百分比有用得多。</p>
<h3>失败集中在当地晚间</h3>
<p>目标地区晚上八点到十一点，失败率明显抬升，其余时段接近正常。这个时段正好是当地网络使用高峰，出口链路拥塞与平台侧负载叠加在一起，两个因素很难完全分开。</p>
<h3>失败类型以超时和 5xx 为主</h3>
<p>超时占多数，其次是 5xx。4xx 很少，说明请求本身没问题，卡在了传输与服务端负载上。这一点很重要：如果是 4xx 为主，方向就该转向请求内容，而不是继续折腾网络。</p>
<h3>重试能救回一部分，但抬高整体耗时</h3>
<p>开启重试后成功率回升，但 P95 延迟翻了一倍多。用户侧的体感是能出结果，但要等很久，这在交互式场景里等于不可用。这条记录直接决定了后面要不要为住宅出口付钱。</p>

<h2>三、第二周记录：住宅出口的代价是什么</h2>
<p>第二周换住宅出口，配置不动。成功率上来了，但也出现了新的问题，这些代价如果不记，结论就会失真，也容易在汇报时被追问。</p>
<h3>延迟的分布更分散</h3>
<p>中位数比机房出口低，但长尾更明显：少数请求会出现两三秒的首字节。原因是住宅线路的路径不固定，绕路的情况比机房多。看平均值会得出住宅更快的结论，看 P99 会发现另一面。</p>
<h3>地址可用率不是满值</h3>
<p>一周里有两次地址不可用，需要切换。机房出口一周内没有出现这种情况。这说明住宅出口的稳定性依赖供应商的池管理，不是天然的属性，选供应商比选类型更重要。</p>
<h3>成本结构完全不同</h3>
<p>机房出口按带宽和实例计费，成本基本固定；住宅出口按流量或地址计费，成本随请求体积波动。请求体大的业务，这个差距会被放大到不可忽视的程度。做对照实验时一定要把账单也记下来，否则只比性能会得出错误结论。</p>

<h2>五、替代方案的取舍边界</h2>
<p>实验结果能说明在这个场景下住宅出口更好，但不能说明所有场景都该换。边界在哪里，需要按业务来判断，而不是照搬别人的结论。</p>
<h3>值得换的信号</h3>
<p>晚高峰失败率高于一成、重试次数持续偏高、业务与用户身份强绑定。三条中占两条，就值得投入。反过来说，如果三条都不占，换过去大概率只是增加了账单。</p>
<h3>不值得换的信号</h3>
<p>失败主要是 4xx、请求体大且对成本敏感、业务是纯内部批处理。这些情况下换出口的收益有限，把精力放在请求体优化和重试策略上更划算。</p>
<h3>中间路线：分流而不是全换</h3>
<p>把与身份相关的请求走住宅出口，批量任务走机房出口，按路径分流。这样既拿到关键场景的稳定性，也控制了成本。分流的关键是标记清楚哪类请求走哪条链路，别让流量随机漂移，否则数据又会混在一起，等于没分。</p>

<h2>常见问答</h2>
<h3>这个实验结果能直接套用到我的业务吗？</h3>
<p>答：不能直接用。地区、时段、请求体大小、并发曲线都会影响结果。可以借用的是方法：控制变量、分段统计、按小时聚合，这套方法在多数场景都成立。</p>
<h3>住宅出口的延迟一定更高吗？</h3>
<p>答：不一定。中位数常常更低，因为住宅线路离目标节点可能更近；但长尾更明显，少数请求会绕路。看 P95 比看平均值更有意义。</p>
<h3>实验要跑多久才有参考价值？</h3>
<p>答：至少覆盖一个完整的业务周期，通常七天。要包含工作日与周末、白天与晚高峰。只跑一天，大概率会得到一个偶然的结果。</p>
<h3>两条链路同时跑会不会互相影响？</h3>
<p>答：会，尤其在配额共享的情况下。建议分时段跑，或者用不同的密钥分开统计，否则失败会互相污染，数据不可用。</p>
